Overview

Outbound is an "assumed breach" Linux machine from Hack The Box. We begin with a set of credentials for a RoundCube webmail interface. A post-authentication Remote Code Execution (RCE) vulnerability in RoundCube (CVE-2023-5631) allows us to gain an initial foothold on the system.

Once on the box, we discover that RoundCube stores encrypted user credentials within PHP session files. By decrypting these sessions, we uncover an SSH password for another user, Jacob. This allows us to establish a more stable shell via SSH.

For privilege escalation, we identify that the user Jacob can run a program called 'Below' with `sudo`. 'Below' is vulnerable to CVE-2023-38802, which can be exploited via symlinks to arbitrarily change file permissions. We leverage this to set `/etc/passwd` permissions to `666`, allowing us to add a new root-privileged user and ultimately achieve full root access.

Key Learnings
  • Exploiting Post-Authentication RCE in RoundCube (CVE-2023-5631).
  • Understanding and decrypting PHP session data to extract sensitive information.
  • Leveraging symlink vulnerabilities in SUID binaries (CVE-2023-38802 in 'Below') for privilege escalation.
  • Modifying critical system files like `/etc/passwd` to gain root access.

Reconnaissance

As with any penetration test, we begin with an Nmap scan to identify open ports and services running on the target machine.

Why this step?

Nmap is fundamental for network reconnaissance. It helps us discover open ports, identify running services and their versions, and gather initial operating system information, which guides subsequent attack vectors.

Command 
nmap -sC -sV -vv -oA outbound 10.10.11.77
  • -sC: Performs a script scan using default Nmap scripts. These scripts often detect common vulnerabilities and provide more detailed information.
  • -sV: Attempts to determine service versions running on open ports. This is crucial for identifying potential version-specific vulnerabilities.
  • -vv: Increases verbosity level (double verbose), providing more real-time output during the scan.
  • -oA outbound: Outputs the scan results in all available formats (normal, XML, Grepable) to files named `outbound.nmap`, `outbound.xml`, and `outbound.gnmap` respectively.
  • 10.10.11.77: The target IP address of the Outbound machine.

CVE Research (CVE-2023-5631)

With the version identified, we search for known vulnerabilities related to RoundCube 1.6.10, specifically looking for RCE or authentication bypasses.

Why this step?

Public exploit databases (like CVE Details, Exploit-DB, Google) are essential resources for finding known weaknesses in software. Searching by product and version can quickly reveal exploitable vulnerabilities.

A search on CVE Details for "RoundCube" reveals CVE-2023-5631, which describes a post-authentication RCE vulnerability in RoundCube versions before 1.5.10 and 1.6.11 due to an unvalidated parameter, allowing deserialization. This perfectly matches our identified version (1.6.10).

Concept: CVE-2023-5631 (RoundCube Post-Auth RCE)

This vulnerability is a Post-Authentication Remote Code Execution (RCE) affecting RoundCube Webmail. It stems from improper validation of a parameter during deserialization, allowing an authenticated attacker to inject arbitrary PHP objects. When these objects are deserialized by the server, they can trigger arbitrary code execution in the context of the web server user.

Concept: Deserialization Vulnerability

Deserialization vulnerabilities occur when an application deserializes untrusted data without proper validation. If an attacker can control the serialized data, they can inject malicious objects that, when deserialized, trigger unintended code execution (like calling system commands), modify application logic, or bypass authentication. This is particularly dangerous in languages like PHP, Python, and Java.

Command

  • --target http://mail.outbound.htb: Specifies the URL of the vulnerable RoundCube instance.
  • --user tyler --pass '[PASSWORD]': Provides the authenticated user credentials required for the post-authentication vulnerability.

    • bash -i: Provides an interactive Bash shell.

Concept: Reverse Shell

A reverse shell is a shell session established from a target machine back to an attacking machine. Instead of the attacker directly connecting to the target (which might be blocked by firewalls), the target initiates the connection. This technique is commonly used to bypass network restrictions and gain interactive control over compromised systems.

Shell Upgrade

The initial reverse shell is not fully interactive. We upgrade it for better usability, including tab completion, clear screen functionality, and job control.

Why this step?

An upgraded shell significantly improves usability during penetration testing. It allows for better command execution, easier navigation, and the use of tools that require a full TTY, making post-exploitation tasks much more efficient.

  • script -q /dev/null bash (Alternative, used in transcript):
    • script: Records all terminal activity.
    • -q: Quiet mode, suppresses start/end messages.
    • /dev/null: Directs the log output to /dev/null to prevent creating log files on the target.
    • bash: The shell to run within the script session.

Payload Analysis (Optional Deep Dive)

The exploit's PHP deserialization payload can be interesting to analyze. Using CyberChef, we can decode the URL-encoded and obfuscated payload.

Why this step?

Analyzing the exploit's payload helps in understanding the underlying vulnerability and how it works. This knowledge can be crucial for detecting similar attacks, developing custom exploits, or performing forensic analysis.

Concept: CyberChef

CyberChef is a web app for "The Cyber Swiss Army Knife" - a simple, intuitive web app for carrying out all manner of cyber operations, from simple data encoding like Base64 and XOR to more complex encryption, decryption, and data analysis. It's an invaluable tool for reverse-engineering payloads.

The exploit also uses a unique boundary string (e.g., `--------CVE-2023-5631-boundary--`) within the HTTP request, which could be used to detect or filter this specific exploit in an active engagement.

Exploiting 'Below' (CVE-2023-38802 - Symlink Abuse)

Researching "below CVE" or "below 0.8.0 exploit" leads to CVE-2023-38802. This vulnerability in `below` allows for arbitrary file permission changes due to its handling of log files. Specifically, `below` creates `/var/log/below` with `777` permissions and then sets `666` permissions on `error_user.log` within that directory.

We can exploit this by: 1. Deleting `/var/log/below/error_root.log`. 2. Creating a symbolic link from `/etc/passwd` to `error_root.log`. 3. Executing `sudo /opt/below/below`. This will cause `below` to attempt to `chmod 666` its log file, but due to the symlink, it will instead `chmod 666` `/etc/passwd`. 4. Once `/etc/passwd` has `666` permissions, we can add a new root user or modify an existing one.

Why this step?

This symlink attack leverages a flawed permission-setting logic in a SUID/sudo-able binary. By manipulating the target of the file operation, we force the privileged program to operate on a critical system file (`/etc/passwd`), granting us write access that we wouldn't otherwise have.

Concept: Symlink Vulnerability

A symbolic link (symlink) is a special type of file that points to another file or directory. Symlink vulnerabilities occur when a privileged program (running as root or with `sudo`) performs operations on a file path that can be controlled by a less-privileged user. If the attacker can replace a legitimate file with a symlink pointing to a critical system file (e.g., `/etc/passwd`), the privileged program might inadvertently modify the permissions or content of that critical file, leading to privilege escalation.

Concept: `/etc/passwd` Modification

The `/etc/passwd` file stores essential user account information. By modifying this file, an attacker can create new user accounts, change existing user IDs (UIDs) to 0 (root), or remove password hashes, effectively gaining root access. It requires write permissions, which are typically restricted to root.

What This Tells Us

The permissions of `/etc/passwd` have successfully been changed to `666` (`-rw-rw-rw-`), meaning any user can now read and write to this critical file! This is exactly what we needed for privilege escalation.

Adding a New Root User

With write access to `/etc/passwd`, we can now add a new user with UID and GID set to `0` (root privileges) and no password.

Why this step?

Modifying `/etc/passwd` to create a new root user (UID 0) with an empty or known password provides immediate and persistent root access. This is the final step in leveraging the `/etc/passwd` write vulnerability.

Command 
echo 'pone::0:0:Pone user:/root:/bin/bash' >> /etc/passwd
  • echo '...': Prints the specified string to standard output.
  • 'pone::0:0:Pone user:/root:/bin/bash': The new user entry for `/etc/passwd`.
    • pone: The username.
    • ::: An empty password hash, meaning no password is required for this user.
    • 0:0: Sets the User ID (UID) and Group ID (GID) to 0, granting root privileges.
    • Pone user: The comment field.
    • /root: The home directory for the `pone` user.
    • /bin/bash: The default shell for the `pone` user.
  • >> /etc/passwd: Appends the new user entry to the `/etc/passwd` file.
What This Tells Us

A new root user named `pone` has been added to the system without requiring a password.

Finally, switch user to `pone` to gain root access.

Command 
su pone
  • su pone: Switches the current user to `pone`. Since `pone` has no password set and root privileges, this command immediately grants root access.
Output 
root@outbound:/home/jacob#
What This Tells Us

We are now `root` on the system!

Lessons Learned

Summary of Key Takeaways
  • Web Application Vulnerabilities: Even well-known applications like RoundCube can harbor critical vulnerabilities. Regular patching and security audits are essential. Post-authentication RCEs often depend on application-specific logic like deserialization.
  • Session Management Security: Storing sensitive data like plaintext or easily decryptable passwords in PHP sessions on the server is a significant security risk. Sessions should only contain identifiers, not credentials.
  • Importance of `sudo` Configuration: Loosely configured `sudo` permissions, especially with wildcards (`*`) or on custom binaries, create prime privilege escalation opportunities. Always audit what commands users can run with `sudo`.
  • Symlink Abuse: Vulnerabilities in privileged binaries that perform file operations (like `chmod` or `chown`) can be exploited using symbolic links to manipulate critical system files (`/etc/passwd`, `/etc/shadow`) and gain root access. This is a classic local privilege escalation vector.
  • Defense in Depth: Multiple layers of defense are crucial. Even if one vulnerability is exploited, subsequent layers (like secure session handling or strict `sudo` policies) should ideally prevent further compromise.
